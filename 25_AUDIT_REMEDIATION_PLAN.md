This changes five things in the plan below:
1. **WP15 moves from P2 to P1** — a full-scale release gate, not deferrable polish. A passing 100-user pilot does not satisfy the 500-user target.
2. **F10** (SSE pool exhaustion) must support 500 live notification identities plus a separate 1,000-stream reconnect scenario with bounded listeners — not just "100 streams don't exhaust the pool."
3. **F29** (rate limits): 1,000 tenant-requests/minute is only 4 requests/user/minute for a 250-user tenant — this specific hardcoded number needs to be replaced with a measured, bounded per-tenant/user/endpoint budget, not just "made consistent."
4. **F11/F12** (report completeness/filter correctness) become load-bearing at 2,000,000 leads — a bigger row cap is explicitly called out as *not* an acceptable fix; needs real SQL-side aggregation.
5. **F18** (job queue fairness): the largest tenant's heavy imports/reports/campaigns must not degrade smaller tenants beyond a proposed 20% p95 margin — this is now a concrete, testable acceptance bar, not just "add tenant fairness."

Full benchmark ramp (10/25/50/100/250/500 users against a fixed 2,000,000-lead dataset, request-rate-vs-concurrent-user-count table, per-tenant fairness SLOs) is specified in `CAPACITY_REQUIREMENTS.md` and belongs to WP15 — not reproduced in full here to avoid drift between two copies.

## Hard constraints (apply to every work package below)

- Never weaken authorization/RLS/validation to make tests pass.
- Never silence build/type errors globally or replace a real implementation with a stub/constant return value.
- Treat authentication, role permissions, tenant scope, field scope, module entitlements and impersonation as distinct controls.
- Keep required business writes, audit and outbox events atomic.
- Use explicit concurrency/idempotency contracts for sensitive transitions.
- Never expose secrets in logs, screenshots, diffs or reports.
- Test real DB behavior with a least-privilege runtime role when claiming isolation/concurrency coverage — mocked query tests are unit tests only.
- Record performance measurements with dataset, concurrency and hardware.
- Preserve complete-data semantics in reports; no silent row truncation.
- The audit's own `audit-reproduction.test.ts` asserts *vulnerable* outcomes as evidence — when fixing F01/F02, invert those expectations into rejection tests; do not treat them as desired behavior.
- The Unnati Vidya website (`apps/unnatividya`) is a separate, independently deployed product sharing only the VPS. Never redesign it, change its data, or restart/redeploy it as an incidental CRM operation. Website fixes (F26/F27, WP16) are their own separately scoped release.
- Do not ask about routine implementation choices. If a business decision genuinely blocks correctness, ask one question at a time (see [Outstanding questions](#outstanding-questions-ask-one-at-a-time) below).
- Priorities (P0/P1/P2) are engineering triage, not CVSS scores. P0 = fix before broadening access. P1 = release-blocking for the next hardening release. P2 = planned performance/maintainability work.

## Architecture and design guidance (sections 5-11 of the audit)

Read in full for this update. Summarized here so it can be cited by task number below instead of re-quoted per package.

**Target architecture (section 5).** Keep the modular monolith — one Next.js web/API process, worker groups, ML and website as separate deployment boundaries, not a service split. Eight shared contracts should emerge as WP04/WP07/WP08 progress, not be built upfront: (1) identity context — subject/session/tenant/actor-impersonator/capability version/effective permissions, explicit system-job context for workers; (2) `authorize(context, action, resource)` plus query constraints, enforced server-side regardless of UI capability summaries; (3) query/filter contract — module registry, typed fields/operators, nested AST, timezone/tenant scope (this is WP09's F12 fix); (4) mutation contract — validated input, expected version, idempotency key, transaction, audit+outbox together (WP08's F13 fix); (5) job contract — name/version/tenant/entity/trace id/retry/lease/entitlement/dedupe (WP10); (6) error contract — machine code, correlation id, no secrets/stack traces (WP11/F29); (7) analytics contract — owner, definition, grain, denominator, permission scope, freshness (WP09); (8) module contract — default availability, dependencies, retention-after-disable (F30/WP04 foundation). Extract `src/modules/<domain>/{schema,service,repository,policy}` gradually, starting with auth/policy/filter-compilation/event-persistence — not a big-bang refactor.

**PostgreSQL design (section 6).** Tenant-aware FKs/composite `(tenantId, id)` uniqueness where warranted (WP07); distinguish person/contact from inquiry/opportunity/application — a learner can inquire about two universities, don't collapse on phone uniqueness (WP13); NUMERIC/integer-minor-units for money, not JS `Number` (WP10/F15); optimistic versions on concurrently-edited/irreversible transitions (WP08/WP10); atomic audit+outbox with the business mutation, mandatory vs optional-analytics failures kept distinct. Index work (WP09/WP15) must be measured first (`EXPLAIN ANALYZE` on staging, not guessed from this doc) — candidate patterns are listed per query type (lead list, owner queue, task due queue, outbox claim, timeline, predictive filter, consent events, custom-field projections). Keyset pagination for high-volume lists/exports; explicit tie-breaking on `createdAt` (leads currently sort by `createdAt` alone). Migration discipline: expand/backfill/validate/contract, test fresh bootstrap AND upgrade-from-deployed-schema, measure lock time on backfills — never disable RLS to make a migration easier (WP07).

**Frontend/counselor UX (section 7, feeds WP12).** Product objective: reduce time-to-correctly-completed-counselor-task (identify next lead → history → call/message → log outcome → schedule follow-up → advance application), not feature count. Persona-aware navigation table given (Counselor/Team lead/Marketing/Admissions ops/Partner/Tenant admin, each with a default workspace and what to keep secondary). **Five journeys to polish first, in order**: (1) fresh lead → first contact, (2) follow-up work queue (due/overdue/upcoming split, one trustworthy next-action indicator), (3) application progression (documents/fee/eligibility/approvals in one contextual panel), (4) team exception resolution (unassigned/stale/breached-SLA/failed-sync, click reaches scoped records not a raw ID), (5) safe bulk work (selected-vs-all-matching scope, exact affected count, preview before dangerous actions). Design system rules: keep Radix/Tailwind, reuse `StandardDialog`/`DataTable`/`ErrorState`/skeletons — do not replace the UI library. Accessibility acceptance: keyboard/screen-reader tests on real pages at ~360/768/1440px, ≥90% task completion target with ≥5 representative users (proposed, not measured). Perf: measure per-route JS/parse/waterfall/interaction-delay; one server-state cache approach with tenant+permission+filter+version cache keys, invalidated on mutation and cleared on logout/tenant switch.

**Hostinger KVM4 deployment (section 8, feeds WP11/WP15/WP19).** First make the single host dependable: record deployed commit/image digest and actual CPU/RAM/disk (don't assume the marketing spec), isolate CRM vs website releases (a CRM-only deploy shouldn't touch the website; Caddy's startup health-dependency between the two apps needs testing), keep Postgres/Redis ports private, restore from off-host backup into a separate environment before calling the host production-ready. Illustrative (not prescriptive) 16 GB memory envelope: OS/proxy 2 GB, Postgres 4 GB, CRM web 2 GB, workers 1.5 GB, Redis 0.5 GB, website+sync 1.5 GB, optional ML 2 GB, reserve 2.5 GB. Connection budget formula given: `web instances × web pool + worker processes × worker pool + realtime listeners + website pools + ML connections + admin reserve` — current defaults are 10 conns/web-process + 3 realtime/web-process, website pool also 10. Full-scale decision: benchmark on KVM4-equivalent staging with website+background load cohosted; if it fails, compare (a) same host with better-bounded services, (b) bigger host if CPU/RAM/I/O-bound, (c) dedicated Postgres with separately budgeted web/worker compute if DB-contention/recovery-bound — no upgrade size prescribed without a benchmark. Staged scale-response table given (stable pilot → growing team → DB pressure → HA → large analytical workload), each with its own trigger condition.

**Performance/reliability targets (section 9, WP15's acceptance bar).** Ordinary read API p95≤300ms/p99≤1s; core mutation commit p95≤500ms; common list-usable p95≤1.5s; complex report ≤3s interactive or async job with no hidden truncation; interaction responsiveness p75 INP≤200ms; LCP p75≤2.5s/CLS≤0.1; notification propagation p95≤2s; immediate job start p95≤10s; auth-revocation propagation ≤60s; zero lost committed events/cross-tenant reads under fault injection; RPO/RTO to be agreed explicitly (illustrative RPO 1h/RTO 4h). All targets reported per-tenant AND platform-wide — an aggregate average must not hide a badly-served small tenant. **What changed and why (F06 cookie migration).** This was the largest single change in the remediation effort so far, so it's summarized in more detail than usual. The three session-issuing routes (login, MFA-verify, change-expired-password) now set `httpOnly: true` on the session cookie and no longer include `access_token` in their JSON response bodies at all. `apiFetch` (the app's shared client-side fetch helper) no longer reads a token from `js-cookie` or builds an `Authorization` header — same-origin `fetch()` calls already carry cookies automatically, so this was mostly deletion. `auth-provider.tsx` was rewritten: it no longer stores or decodes a token client-side (removing both `js-cookie` and `jwt-decode` dependencies from this file entirely) and `login()` now takes no arguments — it's called *after* some other route has already set the session cookie on its own response, and just re-fetches `/auth/me` to learn who's authenticated now. The SSE client (`notification-provider.tsx`) no longer appends `?token=...` to the EventSource URL — the browser attaches the same cookie automatically — and the server route's corresponding token-in-URL fallback was removed entirely (not just deprecated) so a leaked/logged URL can't remain a live credential.

Seven admin pages (`rate-limits`, `security`, `usage`, `retention`, `tenants`, `features-dialog`, plus the login/impersonation pages) had their own raw `fetch()` calls building a manual `Authorization: Bearer ${token}` header read directly from `useAuth()` — these all needed individual updates to drop the header and use `isAuthenticated` instead of `token` truthiness as their data-fetch trigger.

**Impersonation needed the deepest rework.** The previous "exit impersonation" mechanism read the platform admin's own raw session token back out of `sessionStorage` and reapplied it directly — a token sitting in `sessionStorage` is exactly as XSS-exposed as one in a JS-readable cookie, and it was never actually invalidated server-side, just reused (this was true even before today's fix, since the admin's original session was never revoked when impersonation started). A dead, unused second `ImpersonationBanner` component using the identical pattern was found and deleted. The fix: `impersonateTenantUser` (`admin.ts`) now returns `expiresInSeconds`; both routes that call it (`/api/platform-admin/impersonate` and the privileged-action-approval `claim` route) set the returned token as an HttpOnly cookie directly rather than returning it in JSON; and a brand new `POST /api/platform-admin/exit-impersonation` route uses the impersonation session's own `impersonatedBy` reference to look up the original admin, issues them a genuinely new session via the same `issueSessionForUser` flow login uses, and revokes the impersonation session so it can't be replayed afterward. Verified via real Postgres end to end: login → impersonate → confirm impersonated identity via `/auth/me` → exit → confirm restored admin identity → confirm the old impersonation token is genuinely rejected (401) afterward.

**Logout got a real fix too, found while working on this.** It previously only cleared the browser's cookie — the underlying `UserSession` row (and therefore the JWT itself, until its natural 7-day expiry) was never revoked. Verified directly: replaying the exact pre-logout token via a raw `Authorization` header after calling logout now correctly returns 401, proving the session is actually invalidated server-side, not just that the cookie was cleared client-side.

**CSRF protection turned out to already exist.** While researching how to add Origin/CSRF validation for cookie-authenticated mutations (the other half of F06), a `src/proxy.ts` was discovered — Next.js 16's renamed middleware convention — already implementing exactly this, using the `Sec-Fetch-Site` header (a more robust signal than Origin/Referer per its own documentation comment) with sensible exemptions for webhooks, SCIM, public endpoints and the external API. This predates the current audit; no new CSRF work was needed, just confirming it's still correctly wired up (verified: a mutating request through the dev server with a same-origin context succeeds; the mechanism itself was left untouched).

**What changed and why.** A single shared `assertSafeOutboundUrl` validates scheme (http/https only), rejects a short list of known-bad literal hostnames (`localhost` and similar), and — the important part — resolves the hostname via real DNS and checks *every* returned address (not just the first) against the standard blocked IPv4 ranges (loopback, RFC1918 private space, link-local/cloud-metadata, carrier-grade NAT, documentation/reserved ranges) and their IPv6 equivalents (loopback, link-local, unique-local, and IPv4-mapped IPv6). **What changed and why.** `createLeadForTenant` and `updateLeadForTenant` previously ran their essential write (the `INSERT`/`UPDATE` itself) followed by a chain of separate `await`s for the audit log, distribution, automations, webhook/app event enqueueing, NBA refresh, and rollup invalidation — each one independently able to fail, with the enqueue steps' own errors already caught-and-discarded even before reaching the call site's own `.catch()`. A crash or error between any two of these steps left the lead existing with an incomplete trail: no audit row, or an audit row but no webhook ever enqueued for a subscriber genuinely waiting on that event. The fix separates this into exactly the two categories the audit's own text asks for: an atomic core (`withTransaction` wrapping the record write, the mandatory `AuditLog` insert, and `WebhookOutbox` row inserts for any active subscription — one commit or none) and after-commit work (distribution/automations/marketplace events/NBA refresh/rollup invalidation — best-effort, wrapped so a failure there can never roll back or fail out an already-committed lead). Threading the transaction's `client` through `createAuditLog` and `enqueueWebhookEvent` required adding one optional parameter to each — both already accepted `execute`/`query`/`queryOne`'s own optional client parameter underneath, so this was a small, targeted change rather than a rewrite. Idempotency support reuses the exact unique-index-plus-catch-the-real-Postgres-error pattern this session has used elsewhere: a `RequestIdempotencyKey` row is written inside the SAME atomic transaction as the lead, so two concurrent requests racing the same key can't both succeed — the loser's insert hits the unique constraint, and that specific error code (`23505`) is caught and turned into "replay the winner's result" rather than a raw 500.
